# Calling Our SMS Gateway

This covers how to use our self-hosted deployment at `sms.territechnologies.com`.
It is not the general SMS Gateway docs (those live at docs.sms-gate.app and still
apply for request/response shapes) — this is specifically how *we* call *our* server.

## Base URL

```
https://sms.territechnologies.com/api/3rdparty/v1/
```

Note the `/api` prefix — our deployment serves the API under `/api`
(`http.api.path` in `config.yml`). The official cloud puts `api` in the domain
instead (`api.sms-gate.app`), so copy-pasting their examples without adding
`/api` will 404 against our server.

## Authentication

Every call uses HTTP Basic Auth with a **per-device** username and password.
These are generated by the server when a phone registers (Settings → Cloud
Server → toggle on, in the app) and shown on the app's Home tab — they are not
something you choose.

```
curl -u "<device-username>:<device-password>" https://sms.territechnologies.com/api/3rdparty/v1/...
```

A message is always sent *through* a specific registered device (phone), chosen
automatically unless you specify one. If a phone is reinstalled or re-registers,
it gets a **new** username/password and a new internal device ID — the old
credentials stop working. Check the app's Home tab for the current ones.

## Sending a Message

```bash
curl -s -u "<username>:<password>" \
  -X POST https://sms.territechnologies.com/api/3rdparty/v1/message \
  -H "Content-Type: application/json" \
  -d '{"message":"Hello from our server","phoneNumbers":["+263XXXXXXXXX"]}'
```

Response:
```json
{
  "id": "WUJmMghqtOdV1YwQcmkss",
  "deviceId": "Xl_RRBArW0Sgx6hu_A0CW",
  "state": "Pending",
  "recipients": [{"phoneNumber": "+263XXXXXXXXX", "state": "Pending"}],
  "states": {"Pending": "2026-10-07T09:45:27Z"},
  "textMessage": {"text": "Hello from our server"}
}
```

Save the `id` — it's the message ID for checking delivery status.

## Checking Delivery Status

```bash
curl -s -u "<username>:<password>" \
  https://sms.territechnologies.com/api/3rdparty/v1/message/<message-id>
```

The `state` field progresses: `Pending` → `Processed` → `Sent` → `Delivered`
(or `Failed`, with a reason). On a healthy connection this happens in under a
second; if it hangs on `Pending` for more than a few seconds, either the phone
is offline/unreachable, or you're querying a stale device (see note above about
re-registration).

## Other Endpoints (same base URL + auth)

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/message` | List sent messages |
| `GET` | `/message/:id` | Get a single message's status |
| `DELETE` | `/message/:id` | Cancel a pending message |
| `POST` | `/message/inbox/export` | Export inbox messages |
| `GET` | `/device` | List registered devices |
| `DELETE` | `/device/:id` | Remove a device |
| `GET` | `/inbox` | List received SMS |
| `GET` | `/inbox/:id/attachments/:partId` | Download an MMS attachment |
| `POST` | `/inbox/refresh` | Request a fresh read from the device |
| `GET` | `/webhooks` | List webhooks |
| `POST` | `/webhooks` | Register a webhook |
| `DELETE` | `/webhooks/:id` | Remove a webhook |
| `GET` | `/logs` | Fetch device logs |
| `GET` / `PATCH` / `PUT` | `/settings` | Read/update device settings |

## Webhooks (receiving events, instead of polling)

Register one to be notified when a message's state changes or an SMS is
received, instead of polling `/message/:id`:

```bash
curl -s -u "<username>:<password>" \
  -X POST https://sms.territechnologies.com/api/3rdparty/v1/webhooks \
  -H "Content-Type: application/json" \
  -d '{"url":"https://our-app.example.com/sms-webhook","event":"sms:received"}'
```

## What's Different From the Original Cloud Service

- Base URL is our own domain, with an `/api` prefix.
- No traffic ever reaches `sms-gate.app` — wake-ups go over our server's own
  live SSE connection to the phone (Route A), not a third-party relay.
- Device registration requires our `GATEWAY__PRIVATE_TOKEN` — get it from
  whoever manages the server deployment, never commit it anywhere.
- OpenAPI/Swagger docs are **off** in production (`http.openapi.enabled: false`),
  intentionally, so this file is the reference until/unless that's turned on
  for internal use.

## Troubleshooting

- **401 on every call:** wrong or expired device username/password — check the
  app's Home tab for the current ones (they change on re-registration).
- **Message stuck on `Pending`:** likely a stale device ID, or the phone is
  offline/unreachable. Check `GET /device` for the current device ID and
  `updated_at`/last-seen time.
- **Registration itself fails (device onboarding, not sending):** that uses a
  separate private token (`GATEWAY__PRIVATE_TOKEN`), not the per-device
  username/password above.
